# Data

The data layer and the rules around it.

## Files

| File | What |
| --- | --- |
| `src/lib/db/client.ts` | The Neon handle, built on first use so builds run without a URL. |
| `src/lib/db/auth-schema.ts` | Generated by the Better Auth CLI, then `scripts/fix-auth-schema.mjs` makes every timestamp `timestamptz`. Never edited by hand. |
| `src/lib/db/schema.ts` | Everything else. Re-exports the auth schema. |
| `src/lib/db/tables.ts` | Every table classified as tenant or shared. A test fails when one is missing. |
| `src/lib/db/scoped.ts` | `forOrganisation(id)`. The only way application code touches a tenant table. |
| `src/lib/db/privacy-requests.ts` | The deletion request record. |
| `drizzle/` | The migrations, baseline first. |

## Adding a table

1. Write it in `schema.ts` with `organisation_id` not null, a foreign key to `organization` with cascade, and an index that starts with it. Every timestamp is `timestamp("x", { withTimezone: true })`. A column compared as a version, such as `updated_at` on an edit screen, takes `precision: 3`, because Postgres keeps microseconds and a JS Date does not. An author column is nullable with `onDelete: "set null"`, because a person who leaves must not take the organisation's records with them.
2. Add it to `tenantTables` in `tables.ts`, or to `sharedTables` with a line on why it holds no tenant data.
3. Add a block to `forOrganisation()` in `scoped.ts`. Every query includes the scope, and a rule test fails until the block exists.
4. `pnpm test`. Then generate a migration, below.

## Changing the auth tables

Change the config in `src/lib/auth/server.ts`, then `pnpm auth:generate`
on Node 22 or later, then generate a migration.

## Schema changes, by environment

`dev` and any preview branch take `pnpm db:push`, which diffs the schema
and applies it, and never `migrate`. `main` takes `pnpm db:migrate` and
never `push`. The baseline ships in `drizzle/` and setup applies it to
`main` before the first deploy.

A feature that changes the schema runs `pnpm db:generate`, commits the
file it writes, and lands it on `main` before the code that needs it: one
PR that adds columns and migrates, then the PR that uses them. A
destructive change is a third PR, after the old code is gone.

A product that pushed to `main` before it had a baseline has the tables
and no journal. Ask first, then reset the branch from `dev` or insert the
journal row by hand.

## Neon

One project per product. `main` is production. `dev` is local. A preview
that needs its own data gets a branch from `main`. Deleting a branch always asks first.

## Identifiers and time

Ids are text UUIDs generated in the application. Every timestamp is
`timestamptz` in UTC, and the organisation row's `timezone` decides how it
renders. `src/lib/time/` is the only place that does date arithmetic.

## The tests

`tests/unit/scoped.test.ts` runs the real schema in PGlite and proves two
organisations cannot see, change or delete each other's rows, and that a
stale edit is refused. `membership.test.ts` and `privacy-requests.test.ts`
prove the helpers the same way. Extend them for a new table.
